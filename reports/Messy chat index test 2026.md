# Messy chat index test (test 2): can the phone model keep its own index? Pre-registration, November 2026

**Status.** Written before any model call. Code: `brain/messy_world.py` (the world, the questions, the truth) and
`brain/messy_index.py` (the arms, scoring, lines). The offline check passed (section 9). Before any scored run come the
expert review (`research_notes/Messy chat test review 2026/`), a development phase on the dev world, and the freeze
(section 8).

## 1. The question

Test 1 found that Qwen3.5-4B, a phone-sized model, answers questions about a personal notebook at 99.9% when given the
right pages, and at 95.1% without thinking. It does not find those pages:
- word search: 50.2%;
- the whole 5,025-note notebook in its context: 20.4%.

The memory road panel (`reports/Memory road panel 2026.md`) voted 4 of 4 to test the owner's association idea next.
The idea is an index the model writes as messages arrive, made of rows that point back to the raw messages. The panel
gave two conditions:
- the test must be on messy chat, where filing is hard;
- the index must face a fair search agent.

In the test 1 world every note carried the full name, and the moderator showed that filing by name then makes finding
trivial (97–100%). This test asks the real question:

**Can the 4B file a messy life correctly as it arrives (who is "she", which Mira, "my sister", "Kofi's flatmate") and
then find what a vague question needs, better than a good search agent?**

## 2. The world (`brain/messy_world.py`, generated by code)

One user writes short chat messages to their AI over 22 months (1 January 2025 to 31 October 2026). Questions are asked on
1 November 2026. The dev world (seed 101) has:
- 260 people;
- 6,019 messages, about 85K tokens;
- 100 messages deleted at the end.

| Feature | Dev world |
|---|---|
| Close people (mum, dad, sister, brother, partner, best friend, boss, flatmate, grandma, uncle) | 10; median 244 messages each (fan effect) |
| Others | 250, from six circles (work, climbing, choir, street, Spanish class, football); 80 known only through someone |
| Mentions | full name 3,081; first name alone 1,224 (only when it was unambiguous at that moment); "my sister" 966; first name with context ("Mira from work") 678; pronoun 353; through another person ("Kofi's flatmate") 321; nickname 221 |
| Same first names | 30 pairs |
| Near names | 20 pairs (Joao/Joaquin, Mirela/Mirella, Teo/Teodor, ...) |
| Facts | 7 attribute types (job, city, pet, hobby, allergy, car, instrument), several wordings each ("works as a pharmacist" / "fills prescriptions at the chemist's") |
| Changes | plain restatements (only order shows the current value), explicit changes, corrections; 114 retractions |
| Lures | 604 near-misses ("is thinking about getting a ferret", "her mother is a nurse") |
| Links | 722 relation messages; 8 types; at most one of each type per person, so "Kofi's mentor" is unique; written from either side |
| Events | 353 meetings with the user, dated relatively ("yesterday", "on Thursday", "on 12 March") |
| Everyday mentions with no fact | 1,658 ("Mum says hi"); plus 250 messages about nobody |

**The test world adds held-out types:** 2 attribute types (balcony plants, a language being learned) and 2 relation
types (bandmate, godparent) that the dev world never has. So nothing tuned on the dev world can depend on the test
world's slots. The index's kinds are open vocabulary, and no prompt lists a kind.

**Deletions:** 100 messages, each the only source of its fact. No other message mentioning that person contains the value,
which the generator checks.

**Self-checks** (`python brain/messy_world.py --split dev`):
- every question's needed messages exist and are not deleted;
- no deleted value survives elsewhere;
- no two questions share a text.

The dev world and a placeholder test world both pass.

## 4. Arms (all Qwen3.5-4B; vLLM 0.33 on one L40S on Modal, as in test 1)

| Arm | What it does |
|---|---|
| **B** | **Write side:** the 4B reads the messages in order, 20 at a time, thinking off. It sees the people already in the index (up to 40, picked by code from names, nicknames, "my X" phrases, the most recent people for pronouns, and people linked to them) and the 5 previous messages. It writes rows: `#message | person id or NEW: Full Name | kind | value`. Rows are only added. A deleted message's rows are removed with it. **Read side:** the 4B writes the question's clues (name / me / fact / link / ask / time; thinking off). Code finds the people the clues point to: names and nicknames; "my sister"; described facts, matched by meaning against the row and the original message, where every fact must match; at most one link; events by month. It returns the raw messages behind their rows (at most 60, in date order). The 4B answers from them. |
| **nolinks** | B without following links: isolates what the association adds. |
| **oracle** | The same read side over an index built from the truth (right people, canonical kinds, both wordings of each value). Separates filing errors from finding errors. |
| **C** | A search agent over the raw messages. Word search (BM25) and meaning search (bge-small-en-v1.5 on CPU) are fused by reciprocal rank, top 20. **Thinking is on at every step,** including the "enough, or search again?" step that crippled test 1's search2. Up to 3 follow-up searches, at most 60 messages. |
| **pages** | The messages the answer needs plus 20 distractors about the same people (including the same-first-name partner). The reading ceiling. |

- Every arm answers with thinking on (Qwen's thinking sampling, as in test 1, 16K cap).
- B, C and pages also answer with thinking off (greedy, 256-token cap), reported only.
- The answer prompt is the same for every arm: notes with dates, today's date, the question; "not in my notes" if the
  notes don't say; ask which person if ambiguous.

## 5. Lines (decided before any model call; coded in `write_summary`)

Read on the test world, B with thinking on, hard set, automatic score.

| Outcome | Condition |
|---|---|
| **PASS: choose B** (the index written as messages arrive) | all of: B ≥ 85%; B ≥ 0.9 × oracle; desc, who and two each ≥ 75%; B − C ≥ 5 points on desc + who + two pooled, with the paired bootstrap 95% interval above 0; wrong merges ≤ 1% overall and ≤ 3% on same/near-name people; no answer names a deleted value; writing ≤ 1,000 completion tokens per message |
| **C: choose search** (simpler) | everything in PASS holds except the 5-point margin over C |
| **STOP** | B < 70%, or wrong merges > 3%, or any answer names a deleted value. The 4B cannot keep its own index: a bigger model writes it overnight, or the whole notebook is used as a recent window |
| **BETWEEN** | anything else |

**How wrong merges are counted** (`write_quality`):
1. Each index person is assigned the real person it most often stands for, judged on messages that mention exactly one
   person.
2. A wrong merge is a row filed under an index person whose real person is not mentioned in that row's message.
3. The near-name rate counts only rows of people with a same-first-name or near-name partner.

**Reported lines (not part of the decision):**
- Events: B ≥ 70% on the three event kinds.
- Fast path: B with thinking off ≥ 85% on the hard set. If it holds, the phone can answer from the index without thinking.

## 6. Scoring (`score`)

- **Attribute kinds** (named, role, nick, fname_ctx, desc, two, upd): an answer names a value if any of that value's keys
  appear as a word start (for example "prescription" or "chemist" for pharmacist). It is right if it names the right value
  and no other value, except earlier values of the same fact for updates.
- **upd:** stale = names only earlier values.
- **retract:** right if it says the fact no longer holds (or "not in my notes") and names no other value.
- **deleted:** right if it names no value. A **leak** = names the deleted value.
- **who / event_who:** right if the full name is in the answer (or the first name, if no one else has it) and no other
  person's full name.
- **amb:** right if it asks which, or names both people.
- **event_last:** right if any date in the answer has the right day and month (and the right year, if one is given).
- **event_what:** right if the answer names exactly the right activity.
- **Hand audit:** at least 100 wrong answers of B (thinking on) are read. If more than 2% of B's hard-set answers are
  scorer errors, both scores are reported and the audited one decides, as in test 1.

## 7. Reported without lines

- Accuracy by kind and arm.
- Held-out questions separately.
- Retrieval: the share of questions where every needed message was in what the reader saw.
- Filing details:
  - index people vs real people;
  - people split into several ids;
  - facts filed;
  - rows written for lures;
  - rows left elsewhere still carrying a deleted value.
- Cost: completion tokens per answer, the share cut off.
- C's number of searches.

## 8. Development phase, freeze and the test seed

**Before the scored run, allowed on the dev world only.** Run the real model on the dev world, with at most the first
1,500 messages and their questions, plus one full dev run. Then change, only:
- the prompts;
- the parsing of the model's lines;
- the read-side retrieval code;
- the chunk size;
- the candidate list;
- the agent's round count (at most 4).

The world generator, the questions, the scoring and the lines in section 5 do not change after the expert review.

**Freeze.** A commit states "FREEZE" in this report and lists the files. After it, no code or prompt changes.

**Test seed.** `int(<first 8 hex digits of the freeze commit's hash>, 16)`, passed as `--test-seed`. No one can see the
test world before the freeze, because its seed does not exist until then. The test world printed while writing the
generator used a placeholder seed (20261115) that is never used for the scored run.

## 9. Offline check (stub, no model, no GPU)

`python brain/messy_index.py --stub --split dev` runs every arm on the dev world with a stand-in model:
- a writer that misses 5% of facts and misfiles 1%;
- clue lines derived from the question;
- **a perfect reader that answers right only when the messages it needs are in its prompt.**

The stub's accuracy therefore measures the retrieval code alone (`results/messy_index_dev_stub/summary.md`):

| Hard set, perfect reader | Accuracy |
|---|---|
| pages | 100.0% (bookkeeping and scoring consistent) |
| oracle index | 97.4% (desc 92.0, who 93.3, two 100, events 99.7) |
| B with the stub's writer (5% missed, 1% misfiled) | 87.5% (desc 69.3, who 74.7, two 89.4) |
| nolinks | 77.0% (two-hop 0%, as designed) |
| C | not meaningful: the stub's searches only repeat the question |

**What the check found and fixed before this report:**
- A generator bug: a retracted fact could be restated later for close people, producing two questions with the same
  text and different answers. Fixed, and now a self-check.
- Two retrieval weaknesses:
  - "who did I go hiking with in July": event messages were cut off behind other people's messages (38% → 99%);
  - a "from down the street" context missed a word match.
- Question wording no longer gives an unnamed person's pronoun.

**What it shows about B:**
- Described people depend on filing three facts right and on matching a question's wording ("fills prescriptions at the
  chemist's") to the writer's ("pharmacist"). With 5% of facts missed, desc drops from 92% to 69%.
- The decision will turn on the real 4B's filing quality.

## 10. Departures from the panel's merged design (reports/Memory road panel 2026.md, section 6)

| Panel's design | Here | Why |
|---|---|---|
| A (whole notebook) as the reference | dropped | test 1 measured it on the 4B: 20.4% at 5,025 notes, with 73% of answers cut off and about 15 minutes each under load. Repeating it would cost about 6 GPU hours to confirm a known fail |
| A paraphrased slice rewritten by the 27B | several hand-written wordings per fact, plus alias phrases in questions | no 27B endpoint |
| ≥ 120 questions per hard kind | role 53, fname_ctx 93, retract 114, event_who 70 | role is limited by 10 close people × their facts; the others by the world's size |
| Writer thinking (unspecified) | thinking off | a phone could write overnight with thinking, but 315 sequential thinking calls would take hours on the test GPU; if filing fails the merge line, a thinking-on writer is the first follow-up |
| C at the same token budget as B | C's searches all think; tokens reported, not matched | matching budgets exactly needs a run first; the comparison is reported with costs |

## 11. Known limits

- **The world is written by code from templates,** not real chat. Real people are messier: typos, long messages,
  sarcasm, multi-topic messages. The held-out types, the frozen code and the late seed guard against designer's
  advantage only partly.
- **One user, English, 22 months, about 6,000 messages.** Five to six years would be about 3–4 times larger.
- **16-bit weights on a server GPU.** Phone timing and 4-bit weights are untested.
- **The meaning-search model (bge-small, 33M parameters) is part of both B and C.** A better embedder would help both.
- **Questions announce "use memory now".** Noticing by itself that "her teacher cancelled again" is about Mira (the
  founder's risk) is not tested.
